# Muse 产品与普通网页登录基线

核对日期：2026-11-23。用途：纠正“普通登录必须先实现弹窗认证”的未证实前提，约束后续开发顺序。本轮只调研和修正文档，不开发程序或应用依赖补丁。

## 官方来源与产品身份

- [Muse 官方网页](https://muse.ai/)：页面标题为“Muse — Your Personal AI Agent from Meta”；直接提供电话/邮箱登录入口。
- [Meta 官方产品说明](https://ai.meta.com/muse/)：Muse 是个人 AI agent，可对话、处理任务并连接用户授权的应用。工作台只承载其网页，不重新开发 Muse agent 或其云端计算环境。
- [Meta 帮助中心：How to get started with Muse](https://www.meta.com/help/superintelligence/1331373868832401/)：网页和应用均可使用 Meta Account；可用邮箱或电话创建账号，进入后可在 Chat 中发送消息。

通过网页搜索获取上述官方来源，并实际用客户端浏览器打开 Muse 首页；不是只读第三方介绍。官方帮助文章没有在本次获取内容中证明完整验证码/两步验证的页面推进方式。补查官方站点“verification code + email”未返回直接相关结果，不能由此推断该流程不存在。

## 证据分层

| 内容 | 证据与边界 |
| --- | --- |
| 产品身份、网页入口 | 官方网站、Meta产品页与帮助中心相互对应 |
| 初始登录界面 | 实际浏览器看到“登录或创建账户”“手机号或邮箱”和“继续”；当前页为 https://muse.ai/ |
| 初始DOM | 一张form，text输入，autocomplete为username webauthn，提交按钮“继续”；未读取输入值、Cookie、存储或认证响应 |
| 电话/邮箱后输入验证码 | 用户明确说明：发送后在原网页输入；本轮未输入号码或邮箱、未发送验证码 |
| 可选两步验证 | 用户明确说明：有两步验证的账号在原网页继续输入两步验证码；本轮未用真实账号独立验证 |
| 完成后进入agent对话 | 用户说明，与官方帮助中心Chat用法相符；本轮未登录后发送消息 |

“原网页”是当前需求基线，不应自行扩大成所有认证请求、URL、连接器或外链永远不会导航/开新窗口。当前初始页未出现弹窗，也不能单独证明整个登录链从不使用其他来源；后续按真实观察记录。

## 用户确认的主流程

打开该账号的Muse网页 → 输入电话或邮箱 → 点击发送/继续 → 原网页输入验证码 → 如该账号启用了两步验证，在原网页输入两步验证码 → 完成后与Muse agent对话。

页面文案可能因语言/阶段不同。当前实际初始按钮为“继续”，不据此否定用户描述中的“发送”。工作台保持同一账号、同一WebView、同一浏览资料上下文，不代收或代填验证码，不重新实现官网认证表单。

## 对工作台的修正

1. 普通登录优先验证原页流程，不再以通用 `window.open` 接管能力作为开始普通登录验证的前置条件。此前这项前提未经实际产品流程核实，现已撤回。
2. 继续使用稳定账号ID与独立持久化WebView资料，保留当前页面推进，不在验证码/两步验证阶段重建视图。
3. 官网加载完成、Cookie存在或页面标题变化均不等于登录成功。真实登录与服务端会话有效性要人工验收，不能伪造已登录状态。
4. 暂停Tauri/Wry补丁研究；既有实验保留为历史证据，不应用到生产。主登录基线并不因此需要放开远程IPC、自有unsafe或独立认证窗口。
5. 真正出现的连接器认证、文章或新窗口请求仍按来源账号、安全协议和最终同窗要求单独处理。目前生产代码仍拒绝window.open，这是功能缺口，但不是已证实的普通登录依赖。
6. 本次只纠正调研与开发顺序，没有宣称M0通过、登录保持已实现或M1—M6已经交付。

## 下一次实际验收

由用户在正式原生工作台中自行输入敏感信息，操作者不采集密码/验证码/令牌，不在登录后读取聊天内容或批量截图。

- A/B分别在自己的现有网页完成电话/邮箱、验证码和适用的两步验证，人工确认进入对话。
- A → B → A，确认网页和已登录身份不串号；验证过程中不重建页面。
- 仅销毁A视图再用相同资料重建；退出整个应用再启动；分别记录会话是否仍有效，不承诺永久登录。
- A单独退出后B不受影响；过期或服务端安全验证时可在A原网页重新登录。
- 若实际流程出现弹窗或跨来源问题，记录具体阶段和安全错误类别后再决定最小修复，不能预先假定。
